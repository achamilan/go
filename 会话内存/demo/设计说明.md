并发会话 Demo 设计说明
========================

1. 概述
-------
本 demo 演示 Go 运行时 gcdeadtrace 特性的 per-session 对象标记 (v4) 功能。
通过 Actor 模式和并发会话测试，验证多 goroutine 同时开启会话时，
每个会话的分配/释放数据能被独立追踪，不会互相混淆。

2. 架构设计
-----------
2.1 Actor 系统
  - ActorSystem: 管理所有 actor 的生命周期（启动/停止）
  - WorkerActor: 执行分配模式，每个 actor 在独立的 goroutine 中运行
  - MonitorActor: 周期采集内存统计并输出快照

2.2 分配模式
  PatternLoop       — 循环分配，全部死亡（类似 TestGcDeadTrace）
  PatternMixed      — 多分配站点，部分存活/部分死亡（类似 TestGcDeadTraceComplex）
  PatternSession    — 单一会话内分配（类似 TestGcDeadTraceSession）
  PatternFullyDead  — 按站点分析完全死亡（类似 TestGcDeadTraceFullyDead）
  PatternConcurrent — 双并发会话，相同分配站点（新增 v4 测试）

2.3 并发会话测试设计
  - 两个 goroutine 同时开启 GcDeadSessionStart()
  - 从完全相同的分配站点 (make([]byte, 256)) 分配内存
  - Session A: 3 × 256B (全部会死) + 1 × 1024B (存活)
  - Session B: 2 × 256B (全部会死) + 1 × 512B (存活)
  - 两个 session 结束后触发 GC
  - 验证 per-session 分解输出中每个会话数据正确隔离

3. 测试点及预期结果
--------------------

测试点 1: 多会话并发隔离
  - 输入: 两个 goroutine 同时启动会话，从相同站点分配
  - 预期: gcdeadsession by session 输出两个条目，各自 alloc/freed/alive 独立

测试点 2: 会话分配计数
  - 预期:
    Session A (func1): 4 allocs, 1792 bytes = 3×256 + 1×1024
    Session B (func2): 3 allocs, 1024 bytes = 2×256 + 1×512

测试点 3: 会话释放计数 (per-cycle)
  - 预期:
    Session A: 3 freed, 768 bytes = 3×256 (三个 256B 引用被 nil 覆盖)
    Session B: 2 freed, 512 bytes = 2×256 (两个 256B 引用被 nil 覆盖)

测试点 4: 会话存活计数 (累计-累计)
  - 预期:
    Session A: 1 alive, 1024 bytes (concurrentSinkA2 保持引用)
    Session B: 1 alive, 512 bytes (concurrentSinkB2 保持引用)

测试点 5: freed 站点报告
  - 预期: 5 个对象 (1280 bytes) 来自 5 个分配站点
    (func1 的 3 个 make 调用 + func2 的 2 个 make 调用)

测试点 6: alive 站点报告
  - 预期: 2 个对象 (1536 bytes) 来自 2 个站点
    (func1 的 1024B 在 line 758 + func2 的 512B 在 line 768)

4.1 start/end 代码位置标记 + @type 注解 (v5)
---------------------------------------------

每个 session 行末尾附加了 `[start: file:line, end: file:line]` 标记：
  - start: 调用 GcDeadSessionStart() 处的代码位置
  - end:   调用 GcDeadSessionEnd() 处的代码位置
  - session 尚未结束时 end 为空（仅显示 [start: ...]）

此外，freed 和 alive 的站点归属行均附加了 @type 注解:
  - [session #7: 1 objs, 256 bytes @uint8]
  - [session #7: 1 objs, 1024 bytes @uint8]
  - 类型名来自 toRType(typ).string()，如 uint8、[]uint8、main.ListNode

实现原理：
  1. gcDeadSessionInfo 新增 startPC / endPC uintptr 字段
  2. GcDeadSessionStart() 中调用 sys.GetCallerPC() 捕获调用者 PC
  3. GcDeadSessionEnd() 中同样捕获 PC 并写入表条目
  4. gcDeadTracePrint 输出时通过 findfunc()/funcline() 解析为 file:line
  5. mProf_Malloc/gcDeadRecordFree 中 toRType(typ).string() 解析类型名
  6. allocBucketRefs/bucketRefs 携带 typeName 流入输出阶段的 @type

5. 自定义类型分配测试 (PatternCustomTypes)
-------------------------------------------

5.1 设计目的
  验证 gcdeadtrace 能够追踪不同 Go 类型的分配，包括：
  - 结构体 (struct) — 通过 new() 或 &struct{} 分配
  - 切片 (slice) — 通过 make() 分配
  - 映射 (map) — 通过 make() 分配
  - 接口 (interface) — 通过 &struct{...} 赋值给接口变量
  - 字符串 (string) — 通过 string(byteSlice) 转换

7. 正确性分析
--------------

7.1 为什么可以精确归属？
  每个会话分配的对象在 mProf_Malloc 中挂载了 _KindSpecialGcDeadSession 特殊，
  携带 sessionID。GC sweep 阶段 freeSpecial 回调 gcDeadRecordFree，
  通过 sessionID 精确回写对应会话表条目。不再依赖 bucket 级启发式标记。

7.2 为什么共享站点不影响精度？
  func1 和 func2 都调用 make([]byte, 256)，分配相同 size 和相同调用栈，
  本质是同一 bucket。但每个对象独立挂载 special{sessionID: N}，
  释放时根据 sessionID 路由到不同的表条目。
  站点报告虽合并计数，但 per-session 表保持精确。

7.3 同 bucket 新旧会话区分？
  会话表使用 sessionID % gcDeadMaxSessions 索引。
  释放时检查 e.id == sessionID，若索引已被新会话覆盖则忽略旧 special。
  这确保了哈希冲突下不出错。

7.4 Bucket 级启发式误判问题（已修复）
  [问题]
  在 5G 核心网 SMF 产品测试中发现：gcdeadsession:freed 总数（1,052,552）
  远大于 per-session freed 之和（~204,531），差值约 848K（80%）。
  根因是 mProf_Free 使用 bucket 级永久标记来判断对象是否为 session 分配：
  gcDeadSessionAllocBytes > 0 一旦设置就永不清零，导致同 bucket 的所有释放
  （包括非 session goroutine 产生的）都被计入。

  [修复方案：移除 bucket 级启发式]
  采用"方案 A"：完全移除 bucket 级启发式计数，所有 session 数据的 freed 和 alive
  计数完全从 session 表（gcDeadSessionTable）汇总。具体改动：

  - 删除 memRecord 中 6 个 gcDeadSession* 字段
  - 删除 mProf_Free 中的 gcDeadSessionAllocBytes > 0 检查块
  - 删除 gcDeadRawEntry / gcDeadSite 中的 session 计数相关字段
  - gcDeadTracePrint 中 totalSessionFrees/Bytes/Alive 改为从 session 表汇总
  - 站点级 freed 计数改为使用 sessionRefs 各条目 objs 之和
  - 站点级 alive 计数改为使用 aliveSessionRefs 各条目 objs 之和
    （并跟踪 allocBucketRefs.cumFrees 实现准确的 net alive 计算）
  - 交叉引用阶段，session 表引用的 bucket 若不在 raw 条目中则自动创建

  [优点]
  - 消除彻底：不再有 bucket 级启发式，不再有误判
  - 计数一致：总数 = per-session 分解之和
  - 代码简化：移除 6 个 memRecord 字段 + 若干 rawEntry/site 字段

  [测试验证] TestGcDeadTraceBucketOvercount / TestGcDeadTraceBucketOvercountConcurrent
  - 验证同 bucket 的非 session 分配不会被计入 session 释放计数
  - 验证并发 session 场景下正确隔离

8. 运行方式
-----------

  使用预编译的可执行文件（需在 repo 内构建）：

  # 构建
  cd D:/code/go/go/会话内存/demo
  GOROOT=D:/code/go/go D:/code/go/go/bin/go build -o demo.exe main.go

  # 完整 demo（所有 6 种分配模式同时运行）
  GODEBUG=gcdeadtrace=1,gcdeadtracefile=output.txt ./demo.exe -duration=3s

  # 单一模式（专注于某个分配模式）
  GODEBUG=gcdeadtrace=1,gcdeadtracefile=session_output.txt ./demo.exe -mode=session -duration=2s
  GODEBUG=gcdeadtrace=1,gcdeadtracefile=fullydead_output.txt ./demo.exe -mode=fullydead -duration=2s
  GODEBUG=gcdeadtrace=1,gcdeadtracefile=concurrent_output.txt ./demo.exe -mode=concurrent -duration=2s

  # 自动分模式测试（创建 output/ 目录，每个模式独立输出文件）

9. 已知限制
------------

9.1 会话表容量限制 (gcDeadMaxSessions = 64)
  会话表使用固定大小数组 gcDeadSessionTable[64]，按 sessionID % 64 索引。
  当并发 session 数超过 64 时，新 session 会覆盖旧 session 的表条目。
  被覆盖的旧 session 其后续释放数据将丢失（因为释放时检查 e.id == sessionID
  无法匹配）。这将导致：
  - gcdeadsession by session 输出中旧 session 条目消失
  - 该 session 的 freed 计数既不体现在 session 分解中，也不体现在 totals 中
  - 但不会误计到其他 session（检查机制保证安全）
  影响：高并发场景（>64 个 session 同时活跃）下，超出的 session 数据不可追踪。

9.2 Per-Session 分配站点跟踪限制 (gcDeadPerSessionSites = 8)
  每个 session 表条目仅有 8 个 bucketRefs + 8 个 allocBucketRefs 槽位，
  用于跟踪该 session 中不同分配站点的 freed/alive 数据。
  当 session 中的不同分配站点超过 8 个时，多余的站点数据会被 LRU 近似策略
  覆盖（始终写入第一个槽位）。这可能导致：
  - 部分站点的 freed 归属丢失
  - per-session 输出总数正确但 per-site 分解可能不完整
  影响：单一 session 内分配站点极多（>8 种不同调用栈+大小组合）时，
  站点级分解可能不完全准确。

9.3 全局站点行归属限制 (gcDeadSessionRefSlots = 4)
  gcdeadsession:freed 和 gcdeadsession:alive 的站点行中，per-session 归属
  标注最多支持 4 个 session。当超过 4 个 session 从完全相同的分配站点进行
  分配时，只有前 4 个 session 会在该站点行附加 [session #N: ...] 标注。
  影响：大量 session 共享同一分配站点时，归属标注不够完整。

9.4 全局总分配站点数限制 (gcDeadTraceMaxSites = 4096)
  每次 GC 输出时最多聚合 4096 个不同的分配站点。当系统中 session 分配站点
  总数超过此值时，超出部分被丢弃。这影响 freed/alive 站点级报告，但
  不影响 per-session 分解输出（session 表独立于该数组）。
  影响：非常复杂的场景（数千个不同分配站点）下部分站点不出现在报告中。

9.5 调用栈帧深度限制 (gcDeadTraceMaxFrames = 3)
  用于区分分配站点的调用栈最多截取 3 帧（跳过 runtime 帧后）。如果两个
  不同的调用路径在非 runtime 帧的前 3 层相同，则它们被视为同一站点，
  计数合并。
  影响：深层调用路径的站点区分能力有限。

9.6 Per-Session alive 站点计数精度
  站点级 alive 计数使用 allocBucketRefs.frees - allocBucketRefs.cumFrees
  计算 net alive。由于 allocBucketRefs.frees 是 per-cycle 计数（每 GC 循环
  重置），而 cumFrees 是累计值，跨多个 GC 周期后，同一 bucket 在新周期
  的 frees=0 而 cumFrees>0，会导致该站点不再出现在 alive 输出中（正确行为）。
  但若 allocBucketRefs 槽位被新站点的分配覆盖，旧站点的 cumFrees 丢失，
  alive 计数可能会略高于实际（该站点的所有 alive 对象都计入一个 slot，
  实际可能只有部分 alive）。
  影响：长期运行的 session 中，站点槽位被覆盖后 alive 计数轻微偏高。

9.7 类型名称解析精度
  类型名通过 mProf_Malloc 中 toRType(typ).string() 在分配时解析并存储。
  对于匿名结构体、泛型实例化等复合类型，string() 返回的可能是简化的
  类型描述，不一定与源代码完全一致。此外，类型名仅在分配时捕获，
  后续 GC 周期重用时不会更新。
  影响：复合类型的 @type 注解可能不够精确。

9.8 GODEBUG 运行时启用
  gcdeadtrace 特性必须通过 GODEBUG=gcdeadtrace=1 环境变量在进程启动时
  启用，不支持运行时动态开关。启用后 MemProfileRate 自动设置为 1，
  确保所有分配都被采样。这会对性能产生一定影响：
  - 所有 malloc 都走 profiling 路径（mProf_Malloc）
  - 每个 session 分配的 object 挂载 special（addspecial 调用涉及小锁）
  - GC sweep 阶段每个 session 对象的释放都会调用 gcDeadRecordFree
  建议仅用于诊断场景，不建议在生产环境长期开启。
