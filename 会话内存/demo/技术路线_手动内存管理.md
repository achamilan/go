# 基于 gcdeadtrace 的手动内存管理技术路线

## 总览：从诊断到编译的完整闭环

```
 GODEBUG=gcdeadtrace=1       excel_report              alloc_sites.cfg           Go 编译器                运行时
 ┌──────────────┐    ┌──────────────────┐    ┌──────────────────┐    ┌────────────────┐    ┌──────────────┐
 │ 生产/测试运行  │ → │ 解析 gcdeadtrace  │ → │ 生成 fully dead  │ → │ Walk 阶段替换   │ → │ Session      │
 │ 采集分配站点   │   │ 输出 → xlsx + cfg │   │ 站点配置列表      │   │ make/new→alloc  │   │ Arena 分配释放 │
 └──────────────┘    └──────────────────┘    └──────────────────┘    └────────────────┘    └──────────────┘
                                                                                                    │
                                                                                          ┌─────────┴─────────┐
                                                                                          │ 会话开始 → 分配     │
                                                                                          │ 会话结束 → 整块释放 │
                                                                                          └───────────────────┘
```

## 技术点 A：配置生成 — gcdeadtrace → alloc_sites.cfg

| 阶段 | 说明 |
|------|------|
| **输入** | gcdeadtrace 裸输出 + excel_report 已解析的 `Only in Freed (fully dead)` 区域 |
| **输出** | `alloc_sites.cfg`：每条记录含 `file:line`、`func`、`type`、`size` |
| **当前状态** | 设计文档已完成，待实现 |

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| A1. 配置与实际代码不同步（代码行号漂移） | 高 | 中 — 编译器找不到站点 → 退化为正常分配 | 编译时校验：cfg 中的 file:line 若源码不存在则警告并跳过 |
| A2. gcdeadtrace 输出不完整（站点被覆盖） | 中 | 低 — 少优化的部分仍走正常分配 | 多轮采集取并集；excel_report 标注置信度（采样次数） |
| A3. 类型信息不准确（泛型/匿名结构体） | 低 | 中 — 误将含指针类型加入 arena | **严格过滤**：只导出 `[]byte` `[N]byte` `[]uint8` 等明确 noscan 类型；含指针的 type 不导出，归类到 "含指针待人工确认" 清单 |
| A4. 多个 mode 的 fully dead 站点重复 | 低 | 低 — 产生重复 cfg 条目 | excel_report 按 `file:line` 去重；相同站点不同 type 则合并 |

## 技术点 B：编译器集成 — Walk 阶段分配替换

| 阶段 | 说明 |
|------|------|
| **输入** | `alloc_sites.cfg` + `//go:session` 标记的会话边界函数 |
| **动作** | 编译器 Walk 阶段将 cfg 中匹配的 `make()`/`new(T)` 调用替换为 `runtime.sessionalloc()` |
| **关键文件** | `src/cmd/compile/internal/walk/walk.go`（`walkNew`、`walkMakeSlice` 等） |

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| B1. 逃逸分析冲突：本该栈分配的对象被 arena 截胡 | 中 | 低 — 栈分配变 arena，多一次函数调用开销 | 编译器检查：对象大小 ≤ 64B 且已逃逸分析判断可栈分配 → 不走 arena |
| B2. 替换后函数签名/返回值类型不匹配 | 低 | 高 — 编译错误或类型不安全 | 确保 `sessionalloc` 返回值类型与原始 `new(T)` / `make([]T, n)` 一致 |
| B3. 编译器版本升级导致 walk 逻辑变化 | 中 | 中 — 补丁无法直接应用 | 方案与 Go 版本解耦：使用 `//go:linkname` + 运行时替换，而非编译器补丁（见备选方案） |
| B4. 条件编译负担：加/不加 `GOEXPERIMENT` 两套行为 | 中 | 中 — 测试覆盖双倍 | 所有修改加 `if !sessionAllocEnabled { return oldPath }` 守卫；不加 experiment 时零行为变化 |

### 备选方案：运行时替换（无需改编译器）

如果不动编译器，可以通过 `//go:linkname` + 函数指针替换实现：

```go
//go:linkname runtimeNewObject runtime.newobject
func runtimeNewObject(typ *_type) unsafe.Pointer

var sessionAllocHook func(typ *_type) unsafe.Pointer

func init() {
    sessionAllocHook = runtimeNewObject  // 默认 = 正常分配
}

// 会话开始 → 切换 Hook
func SessionStart() {
    sessionAllocHook = sessionArenaAlloc
}

// 会话结束 → 恢复
func SessionEnd() {
    sessionArenaAlloc.Reset()
    sessionAllocHook = runtimeNewObject
}
```

**优点**：零编译器改动，仅 runtime 补丁
**缺点**：`//go:linkname` 不稳定；无法做到"按站点精确替换"（只能全局替换）

## 技术点 C：运行时 Session Arena

| 阶段 | 说明 |
|------|------|
| **设计** | 每个 session 持有一个 bump allocator，从预分配大块中切分 |
| **接口** | `arena.Alloc(size) unsafe.Pointer` → 返回未初始化内存 |
| **释放** | `arena.Reset()` → off 归零，整块可复用（不归还 OS，减少 syscall） |

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| C1. 误分配含指针对象 → GC 不扫描 → 野指针 | 低 | 极高 — 内存损坏/crash | 编译时按 type noscan 过滤；运行时加 `debug` 断言检查；初期仅白名单类型允许 |
| C2. 对象逃逸出 session 生命周期 | 中 | 高 — 会话结束后仍在引用已释放内存 | 逃逸分析标记 `//go:session` 函数返回值及 `go func()` 的参数不得引用 arena 对象；运行时可用 `leak detection` 辅助 |
| C3. Arena 大小不足 | 低 | 中 — 运行时 OOM 或 fallback | Arena 初始化时预分配可配（如 64KB）；耗尽时自动 fallback 到堆分配 + 警告 |
| C4. 并发安全：多个 goroutine 共享同一 arena | 低 | 中 — 竞态 | arena 设计为 per-P 或 per-goroutine；Arena 访问在 `//go:session` 函数内无需锁（串行访问） |
| C5. 内存碎片（session 大小悬殊） | 低 | 低 — 整块释放无碎片 | Bump allocator 无内部碎片；不同 size class 用独立 arena |

## 技术点 D：安全护栏与验证

| 阶段 | 说明 |
|------|------|
| **目标** | 确保手动内存管理的正确性，即使配置出错也不导致 crash |
| **手段** | 编译时检查 + 运行时断言 + 集成测试 |

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| D1. 配置错误地将含指针类型加入 arena | 中 | 高 | **三道防线**：① 编译时 type noscan 检查；② 运行时 `runtime.sessionalloc` 内二次断言 `!typ.ptrdata`；③ 测试：生产 full trace 模式运行，验证无 arena 指针泄漏 |
| D2. 测试无法覆盖所有生产路径 | 中 | 中 | 渐进式上线：只启用 freed == alive 的站点（零存活，绝对安全），稳定后再放开到 partial freed |
| D3. 生产环境内存异常无法定位 | 低 | 高 | Arena 内存区域标记特殊 pattern（如 `0xABABABAB`），crash 时可从 dump 中识别出 arena 对象 |
| D4. GODEBUG=gcdeadtrace=1 在生产开启的性能损耗 | 高 | 中 | gcdeadtrace 仅用于诊断阶段采集配置；配置生成后可关闭 gcdeadtrace，正常运行时不依赖它 |
